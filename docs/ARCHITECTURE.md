# Sakthimaan Crackers Admin: Architecture

Phase 1 (revised after review), Phase 2 (backend foundation, section 8) and Phase 3 (catalogue and inventory, section 9). The data models, pricing/GST engine, numbering and RBAC matrix are real, tested code:

- Shared domain logic: [packages/shared/src](../packages/shared/src). This holds enums, RBAC, order workflow, money/rounding, the GST pricing engine, document numbering, and WhatsApp/UPI links.
- Mongoose schemas and indexes: [apps/api/src/models](../apps/api/src/models)
- Tests: `packages/shared/src/*.test.ts` (unit) and `apps/api/tests/models.test.ts`. The model tests run on an in-memory MongoDB replica set.

The API serves **two clients**:

1. The admin panel in this repo, under `/api/v1/...` (JWT auth).
2. The customer website in the separate `sakthimaan-crackers` repo, under `/api/v1/public/...` (no auth, separate CORS, rate limits and captcha hook).

## 1. Key design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                   | Why                                                                                                                                                                                                                                                                                                                                                  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Money is integer paise.** Percentages are converted to integer **basis points** before any arithmetic.                                                                                                                                                                                                   | Exact totals. Immune to float artefacts such as `100 − 82.3 = 17.700000000000003`.                                                                                                                                                                                                                                                                   |
| 2   | **`computeNetPrice(mrp, discount%, rounding)`** in `shared` is the only net-price formula. Rounding is configurable: `nearest_rupee` (default) or `nearest_paisa`, with halves rounding up.                                                                                                                | The UI preview equals what the API stores. ₹199 at 82.5% → ₹34.825 → **₹35.00** (rupee) or **₹34.83** (paisa). The rounding mode lives in `settings.pricing`. Changing it recomputes every product's `netPrice` (with a preview count first).                                                                                                        |
| 3   | **Prices are GST-inclusive. Taxable value is back-calculated per line**, after allocating any coupon discount across lines (largest-remainder method, exact to the paisa).                                                                                                                                 | Matches how Sivakasi price lists are printed. The invariant `taxable + tax = gross` holds on every line and total (tested).                                                                                                                                                                                                                          |
| 4   | **GST comes from data, never hardcoded.** `hsn`/`taxRate` live on the product (null = inherit), then the category, then settings (default **3604 / 18%**, configurable for the accountant). Seller state is **TN (GST code 33)**: intra-state buyers get **CGST + SGST**, inter-state buyers get **IGST**. | The rate can change without a deploy. `resolveTax()` gives the effective value, which is snapshotted on order lines.                                                                                                                                                                                                                                 |
| 5   | **Delivery/packing charges are a composite supply.** They take the principal goods' HSN and rate and appear in the same HSN-summary row.                                                                                                                                                                   | The standard GST treatment when the seller bills transport with the goods. With `to_pay` delivery the charge is 0 and is paid to the transporter.                                                                                                                                                                                                    |
| 6   | **Round-off line.** Grand total = gross rounded to the nearest rupee, and `roundOff` (−₹0.49…+₹0.50) is stored and printed.                                                                                                                                                                                | Common invoice practice. The breakdown stays reconcilable.                                                                                                                                                                                                                                                                                           |
| 7   | **Order lines are complete snapshots.** Each line stores name, SKU, category, HSN, MRP, discount %, net price, tax rate, unit, quantity, and the per-line taxable/CGST/SGST/IGST. Nothing is re-read from the product.                                                                                     | Editing or deleting a product, or reusing its SKU, can never change an existing order or invoice. A test covers exactly this.                                                                                                                                                                                                                        |
| 8   | **Invoices and credit notes are separate, immutable collections.** Each is a full snapshot of seller (GSTIN, licence), buyer, lines, HSN summary and totals.                                                                                                                                               | Reprints years later stay identical even after the company profile changes. Query updates and deletes are blocked by an `immutablePlugin`. The only permitted change is an invoice becoming `cancelled` by a credit note.                                                                                                                            |
| 9   | **GST-compliant numbering.** At most 16 characters, letters/digits/`-`/`/` only, consecutive per financial year (April–March, evaluated in IST). Invoice `SMC/26-27/00042` (15 chars). Credit note `CN/26-27/00001` (14 chars).                                                                            | Numbers come from a `Counter` (`invoice:26-27`) incremented **inside the issuing transaction**. An aborted transaction consumes no number (tested), so there are no gaps. Unique indexes on `number` and `(financialYear, seq)` mean a number can never be reused. Formats are validated so the longest possible number still fits in 16 characters. |
| 10  | **Cancelling after invoicing issues a credit note.** It is created in the same transaction as the cancellation, mirrors the invoice lines, and marks the invoice `cancelled`. The invoice is never edited or deleted.                                                                                      | Required by GST. Orders that have an invoice cannot be soft-deleted.                                                                                                                                                                                                                                                                                 |
| 11  | **Stock is deducted at _Confirm_.** This uses a transaction with a conditional atomic `$inc` (`stock ≥ qty`) per line plus a ledger row. Enquiries hold no stock. Their **pending demand** is shown per product on the inventory screen.                                                                   | On a shortage, Confirm fails with `409 INSUFFICIENT_STOCK` and `details.items[] = {productId, sku, name, requested, available, shortBy}`, so staff can edit or substitute lines. `stockCommitted` makes both deduction and restock idempotent.                                                                                                       |
| 12  | **Two concurrency mechanisms.** (a) Order-driven deductions use atomic conditional updates. (b) Manual absolute stock edits, order edits and settings use optimistic concurrency (`stockVersion`, Mongoose `optimisticConcurrency`). A stale write returns `409 CONFLICT`.                                 | (a) has no lost updates under Diwali-peak contention. (b) stops two staff overwriting each other during phone edits.                                                                                                                                                                                                                                 |
| 13  | **Gift boxes are Products with `type: 'combo'` and `stockMode: 'own'`**: factory pre-packed, with their own stock. `components` is reserved and rejected by validation for now.                                                                                                                            | Price list, orders, invoices and reports need no special cases.                                                                                                                                                                                                                                                                                      |
| 14  | **Packing before payment is a guarded transition.** `confirmed → packed` requires `orders:pack` **and** `orders:pack_unpaid`, **and** `customer.creditAllowed`. Every use is audited as `pack_unpaid` and flags the order `packedOnCredit`.                                                                | The default is strict. Credit is an explicit, per-customer, audited decision. Toggling `creditAllowed` needs `customers:credit` and is also audited.                                                                                                                                                                                                 |
| 15  | **No payment gateway.** Payments are manual (UPI, bank transfer, cash) with a reference (UTR) and an optional screenshot. Customers may submit proof from the website (`submitted`), and staff verify it (`recorded`) or reject it. Records are never edited, only voided. `kind: refund` covers refunds.  | Only `recorded` payments count toward `amountPaid`. A UPI QR is generated from `settings.payment.upiId` (or uploaded) and shown on the storefront and invoice.                                                                                                                                                                                       |
| 16  | **No WhatsApp/SMS provider.** Staff get generated **click-to-WhatsApp links** (`wa.me/91…?text=`), rendered from the notification templates. The provider-agnostic `NotificationProvider` interface stays for later.                                                                                       | Zero cost. Staff send from their own WhatsApp.                                                                                                                                                                                                                                                                                                       |
| 17  | **Images on Cloudinary** behind a `StorageProvider` interface, with a local-disk driver for development. **No Redis**: the dashboard cache is in-memory behind a `CacheProvider` interface.                                                                                                                | As approved. Either can be swapped later without touching services.                                                                                                                                                                                                                                                                                  |
| 18  | **Soft delete uses an `isDeleted` boolean** plus `deletedAt`/`deletedBy`, enforced by a query plugin. Unique indexes are partial on `isDeleted: false`.                                                                                                                                                    | A deleted SKU, phone number or email can be reused. Aggregations must start with `activeMatch`.                                                                                                                                                                                                                                                      |
| 19  | **Order timeline, payments and audit log are separate collections.** The audit log is written explicitly by services.                                                                                                                                                                                      | Comments don't bump the order version. Each audit entry has the actor, request ID and a field-level diff.                                                                                                                                                                                                                                            |
| 20  | **Roles fixed in code with granular `resource:action` permissions.**                                                                                                                                                                                                                                       | One source of truth for API middleware and UI gating. Order transitions declare their permissions in `transitionRequirements()`.                                                                                                                                                                                                                     |
| 21  | **Refresh tokens are opaque, hashed, rotated, with family reuse detection.** The access JWT lives about 15 minutes and carries `tokenVersion`.                                                                                                                                                             | Reusing a rotated token revokes the whole family. Bumping `tokenVersion` ends every session for that user.                                                                                                                                                                                                                                           |
| 22  | **Serviceability resolves as City override → State → Zone → store default.**                                                                                                                                                                                                                               | Cities only store exceptions, such as a city where crackers are banned.                                                                                                                                                                                                                                                                              |
| 23  | **MongoDB is always a replica set.** Tests use mongodb-memory-server. Development uses the Atlas dev cluster (or the offline `npm run db:local` fallback). Production uses Atlas. docker-compose (`rs0`) is verified in CI from Phase 8.                                                                   | Transactions behave the same everywhere.                                                                                                                                                                                                                                                                                                             |
| 24  | **PDFs use `pdfmake`** (pure JS), rendered from the invoice and credit-note snapshots.                                                                                                                                                                                                                     | Runs on small Render/Railway/VPS instances without Chromium.                                                                                                                                                                                                                                                                                         |
| 25  | **ESM + strict TypeScript 5.9, npm workspaces, Vitest.** `shared` exposes a `source` export condition, so tests and dev run against TS sources without a build.                                                                                                                                            | TS 7 is newer than parts of the lint/Vite chain, so the upgrade is left for later.                                                                                                                                                                                                                                                                   |

### Critical flows (each runs in one transaction; notifications happen after commit)

```
CONFIRM (enquiry → confirmed)
  for each line: Product.updateOne({_id, stock ≥ qty}, {$inc: {stock: −qty, stockVersion: 1}})
                 0 matched → collect shortage
  any shortage → abort → 409 INSUFFICIENT_STOCK { items: [{sku, name, requested, available, shortBy}] }
  ledger rows (order_deduct) · status=confirmed · stockCommitted=true · coupon redemption · customer stats
  activity + audit

ISSUE INVOICE (confirmed or later, once per order)
  Counter $inc "invoice:<FY>" → number via settings.invoice.format (validated ≤ 16 chars)
  Invoice.create(full snapshot from order + current company settings) · order.invoice = {id, number, issuedAt}

CANCEL (any status before dispatched)
  if stockCommitted → restock each line (+ ledger order_restock) · stockCommitted=false
  if invoice issued → Counter $inc "credit_note:<FY>" → CreditNote.create(mirror of invoice)
                      invoice.status=cancelled, cancelledBy={creditNote, number, at} · order.creditNotes.push
  release coupon redemption · status=cancelled · activity + audit

PACK UNPAID (confirmed → packed)
  require permissions orders:pack + orders:pack_unpaid AND customer.creditAllowed (else 403 / 409 CREDIT_NOT_ALLOWED)
  status=packed · packedOnCredit=true · activity packed_on_credit · audit action pack_unpaid

RECORD / VERIFY PAYMENT
  Payment(recorded) · recompute amountPaid/paymentStatus from recorded rows
  if fully paid and status=confirmed → payment_received · customer.stats.totalSpent
```

**Order workflow:** `enquiry → confirmed → payment_received → packed → dispatched → delivered`. A credit customer can also go `confirmed → packed` directly (guarded, see above). Any state before `dispatched` can go to `cancelled`. Items, address and pricing are editable only in `enquiry`.

**Checkout mode** (settings switch): website orders are created directly as `confirmed`, so stock is committed at placement. The customer pays by UPI or bank and submits proof. Orders still unpaid after `settings.order.autoCancelUnpaidCheckoutHours` (default 48) are auto-cancelled and restocked. In **enquiry mode**, website orders arrive as `enquiry` and staff confirm them by phone.

## 5. API endpoints (`/api/v1`)

Every response uses the envelope `{ success, data, meta?, error?: { code, message, details } }`. Cursor lists return `meta.nextCursor`; offset lists return `meta.page/pageSize/total`.

**System:** `GET /health` (liveness) · `GET /health/ready` (DB ping) · `GET /api/docs` (Swagger UI) · `GET /api/openapi.json`

## 8. Phase 2: backend foundation

What exists now: config, DB connection, auth + RBAC, error handling, logging, security middleware, OpenAPI docs, health and graceful shutdown, and tests. Module routers (products, orders, …) plug into `routes/v1/index.ts` from Phase 3 on.

### Request pipeline (`apps/api/src/app.ts`)

```
pino-http (request id: incoming X-Request-Id if well-formed, else UUID; echoed in X-Request-Id)
→ helmet → /health, /health/ready → /api/docs + /api/openapi.json (non-production by default)
→ CORS (public origins for /api/v1/public, admin origins + credentials for the rest)
→ compression → express.json (1 MB) → cookie-parser → mongo-sanitize
→ /api/v1/public: public read limiter → router (writes add strict write limiter + captcha)
→ /api/v1: admin limiter → /auth (own guards) | authenticate → module routers (requirePermission per route)
→ 404 → central error handler (one envelope for every error)
```

### Decisions

| Topic             | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Why                                                                                                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework         | **Express 5**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Rejected promises from async handlers reach the error handler natively, so there are no `asyncHandler` wrappers.                                                                                                                             |
| Config            | All env vars are validated by Zod at startup (`config/env.ts`). Production refuses weak settings: bcrypt < 12, insecure cookies, no admin CORS origins, console mailer.                                                                                                                                                                                                                                                                                                                                                                                                                                | Misconfiguration fails at deploy time with a list of problems, not in the middle of the season. `.env.example` documents every variable.                                                                                                     |
| Validation        | `validated({ body, query, params }, handler)` parses input with the shared Zod schemas and passes **typed** values to the controller. Body schemas are `strictObject`, so unknown keys are rejected.                                                                                                                                                                                                                                                                                                                                                                                                   | One pattern for every route. Field-level `details[]` (`location`, `path`, `message`) let the UI mark the exact input.                                                                                                                        |
| NoSQL injection   | Own `mongoSanitize` middleware strips `$`-prefixed and dotted keys recursively from body, params and query. Re-presenting the old token inside the window returns **that same pair**, as long as the replacement is still live. Outside the window, or once the replacement has itself been rotated or logged out, **reuse revokes the whole family**. | Two tabs or a retried request no longer log the user out, while a stolen old token is still caught. Env validation rejects a `COOKIE_DOMAIN` on shared hosting domains and admin origins outside `COOKIE_DOMAIN`. Everything else uses the Bearer header, which browsers never attach automatically.                                                                                                                                                                                                                                                                                                                                                                                                                     | SameSite alone is not enough once `none` is needed for cross-site hosting.                                                                                                                                                                   |
| Lockout           | 5 failed attempts lock the account for 15 min (`423 ACCOUNT_LOCKED` with `Retry-After`). Unknown email and wrong password return the identical `401 INVALID_CREDENTIALS`, and a dummy bcrypt compare equalises timing. Disabled status is revealed only after a correct password. ## 9. Phase 3: catalogue and inventory

Categories, products, gift boxes, inventory, bulk pricing, image storage, CSV/Excel import and export, and the price list PDF. All endpoints are listed in section 5 and in Swagger (`/api/docs`).

### Decisions

| Topic                 | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Why                                                                                                                                                                             |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **One stock path**    | `InventoryService.apply()` is the only code that changes stock: manual movements, opening stock, imports and (Phase 4) order deduct/restock. It always runs inside the caller's transaction. Decreases use `findOneAndUpdate({ stock: { $gte: qty } }, { $inc })`. Adjustments set an absolute value only if `stockVersion` still matches. Every change appends ledger rows whose `balanceBefore`/`balanceAfter` chain exactly.                                                                                                                                                                                                                                  | Stock can never go negative, even with concurrent orders (tested with 6 parallel stock-outs on 10 units: exactly 3 succeed). The ledger always reconciles with `product.stock`. |
| Batches (optional)    | Per product (`trackBatches`). Stock-in requires a lot number (upserted by lot). Stock-out consumes the **oldest batch first (FIFO)**, writing one ledger row per batch. Adjustments name the batch. Turning tracking on for a product that already has stock creates an `OPENING` batch for it. Deductions return their batch allocations so Phase 4 can restore exactly those on cancel.                                                                                                                                                                                                                                                                        | Batch sums always cover stock, so FIFO deductions can't fail later.                                                                                                             |
| Two kinds of versions | `__v` (Mongoose `optimisticConcurrency`) guards **product edits**: details, price and images. The client sends `version`. `stockVersion` guards **absolute stock adjustments**. Stock movements never bump `__v`, so a stock-in doesn't invalidate an open edit form.                                                                                                                                                                                                                                                                                                                                                                                            | Staff editing product details and staff receiving stock don't block each other.                                                                                                 |
| Price changes         | `PATCH /products/:id/price` (needs `products:update_price`) is separate from detail edits (`products:update`), and every change is audited as `price_change` with the MRP/discount/net/tax diff. Detail edits reject `mrp`, `stock` and other price fields (strict schema).                                                                                                                                                                                                                                                                                                                                                                                      | Inventory staff can maintain product data without touching prices.                                                                                                              |
| Bulk price            | Filter by categories (including sub-categories), product IDs or type. Either "set discount %" or "adjust MRP ±%" (rounded to whole rupees). The preview is computed with the same `computeNetPrice()` and rounding as single edits. Apply writes each row only if its MRP and discount are still what was previewed. **One mismatch rolls back the whole change** (409). Each product gets a `price_change` audit entry.                                                                                                                                                                                                                                         | "80% on all sparklers" is safe at peak season.                                                                                                                                  |
| Tax inheritance       | Product → sub-category → category → settings (`resolveTax`). The API returns both the override (`hsn`/`taxRate`, null = inherit) and the resolved `effectiveTax`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | The admin UI shows what will actually be charged. Phase 4 snapshots `effectiveTax` onto order lines.                                                                            |
| Gift boxes            | `type: combo` with `comboItems` (singles only: no nesting, no self-reference) and their own stock (`stockMode: own`). **Price suggestion:** box MRP = Σ item MRPs (rounded up to the rupee), and the discount is chosen so the box net price ≈ Σ item net prices, minus an optional extra bundle %. A product that sits inside a box can't be deleted.                                                                                                                                                                                                                                                                                                           | Matches factory pre-packed boxes. The suggestion is a starting point the user can adjust.                                                                                       |
| Delete / restore      | Soft delete, with a "deleted" filter on the list (`products:delete`). Restore fails with `DUPLICATE` if the SKU or slug was reused meanwhile.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Old orders keep their snapshots, and nothing is lost by mistake.                                                                                                                |
| Images                | Multipart upload → **file type detected from bytes** (JPEG/PNG/WebP/AVIF only) → **re-encoded with sharp** to WebP (max 1600 px, EXIF/GPS stripped, appended payloads dropped, 40 MP decompression-bomb limit) → `StorageProvider`. **Cloudinary** in production (CDN transforms via shared `imageUrl()`). **Local disk** in development, served at `/uploads` with `Cross-Origin-Resource-Policy: cross-origin`. Max 8 images per product, enforced atomically. A failed save deletes the orphaned upload.                                                                                                                                                      | Uploaded files are never stored or served as received.                                                                                                                          |
| Import                | CSV (UTF-8 with or without BOM, `,` or `;` delimiter) or `.xlsx` ("Products" sheet), max 2 MB / 2000 rows. Each row is parsed with the shared `parseImportRow()`, which accepts what people type (`₹1,299.50`, `82.5%`, `Yes`). Categories match by name, case-insensitive (optionally created). SKU = update key. **Dry run** returns a row-by-row report. **Apply is all-or-nothing:** any error → 422 with the report and nothing saved. Otherwise categories, creates, opening stock, updates (conditional on `__v`) and audit entries commit in **one transaction**. Gift boxes are excluded (built in the UI). Opening stock applies to new products only. | The client can send a sheet and fix it by row number. A half-imported catalogue can't happen.                                                                                   |
| Export                | Same columns as import, plus read-only `net_price` and `current_stock`. CSV has a BOM and CRLF (Excel-friendly). XLSX has dropdowns and instructions. **Formula injection is neutralised** (`=`, `+`, `-`, `@` prefixed with `'`), and import undoes exactly that, so export → edit → import round-trips with no changes (tested).                                                                                                                                                                                                                                                                                                                               | Bulk editing in Excel is safe.                                                                                                                                                  |
| Templates             | `docs/templates/product-import-template.{csv,xlsx}` + `PRODUCT_IMPORT_GUIDE.md` for the client. Generated from the shared column definitions (`npm run templates -w @sakthimaan/api`). A test fails if the committed CSV drifts from the generator. `GET /products/import/template` serves the same, with the store's current categories in the dropdown.                                                                                                                                                                                                                                                                                                        | One source of truth for the format.                                                                                                                                             |
| Price list PDF        | pdfmake (pure JS) with the bundled Roboto font (has ₹). Network and other local files are blocked. A4, company name, address, licence number and GSTIN in the header, the season name in the title. Grouped by category → sub-category in display order. Columns: # · Product (GREEN / OUT OF STOCK tags, box contents) · Content · MRP (struck through) · Disc % · Net · empty **Qty** and **Amount** for paper orders. Page X of Y footer. Options: one category, hide out-of-stock, hide gift boxes.                                                                                                                                                          | The business's main sales document, printable and shareable on WhatsApp.                                                                                                        |
| Pending demand        | Quantity on open **enquiries** per product (they hold no stock) is shown on the product list and detail (`pendingDemand`). `GET /inventory/demand` lists demand vs stock with `shortBy`, so staff can restock before confirming.                                                                                                                                                                                                                                                                                                                                                                                                                                 | As agreed: enquiries don't reserve stock, but the demand is visible.                                                                                                            |
| Settings cache        | 30 s in-process cache of the settings singleton (tax defaults, low-stock default, company info for the PDF). Invalidated by the settings service (Phase 5).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Avoids a DB read on every catalogue request.                                                                                                                                    |

## 10. Admin UI (frontend foundation + catalogue screens)

The plan changed after Phase 3: the UI is built now, then each module is built API + UI together. Orders/Enquiries is next.

### Stack and structure

React 19 · Vite · TypeScript (strict) · Tailwind CSS v4 · shadcn/ui (Radix, "Nova" preset, saffron brand colour) · React Router v6 · TanStack Query · TanStack Table v8 · Zustand · React Hook Form + Zod.

```
apps/admin/src/
  app/App.tsx            router (lazy-loaded pages), query client, providers
  lib/                   api client, session (single-flight refresh), format, download, theme
  components/            layout (shell, permission-aware nav), guards, common UI, confirm dialog
  components/ui/         shadcn/ui (generated; excluded from lint/format)
  features/<module>/     pages + components; features/catalog/api.ts holds the query hooks
```

### Decisions

| Topic                     | Decision                                                                                                                                                                                                                                                                                                                                                                    | Why                                                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| React 19 (spec said 18)   | The current shadcn/ui components pass `ref` as a normal prop, which React 18 silently drops. That breaks Radix focus handling in dialogs and menus.                                                                                                                                                                                                                         | Keeps shadcn's maintained components as they are. React Router stays on v6 as specified, with the v7 future flags on so a later upgrade is painless. |
| Session                   | The access token is held **in memory only** (Zustand). On load, the app restores the session through `POST /auth/refresh` using the httpOnly cookie.                                                                                                                                                                                                                        | An XSS bug cannot read a long-lived credential from storage.                                                                                         |
| **Single-flight refresh** | A 401 triggers one refresh shared by all concurrent requests in the tab, serialised **across tabs with the Web Locks API**. A tab that waited reuses a token another tab already obtained, received over **BroadcastChannel**. Logout and session changes are broadcast to every tab. Without Web Locks it falls back to in-tab dedupe plus the server's 30 s grace window. | Verified in a headless browser: two tabs refreshing at the same moment both stay signed in.                                                          |
| Shared logic              | Forms validate with the same Zod rules as the API. The net-price/GST preview uses the shared `computeNetPrice`, `resolveTax` and `splitInclusiveGst`, so the preview equals what the API stores. Field errors from the API (`details[].path`) land on the matching input.                                                                                                   | No second implementation of pricing rules.                                                                                                           |
| Permissions in the UI     | The nav, buttons and pages are gated by the user's permissions (`useAuth().can`, `<Can>`, `<RequirePermission>`). Price fields are read-only without `products:update_price`. A draft's "Active" switch is locked for users who can't approve prices. The API remains the enforcement point.                                                                                | Each role sees only what it can do. Unbuilt modules show as "Soon" so the roadmap is visible.                                                        |
| Draft rule (API)          | Products created by a user without `products:update_price` are saved **inactive (draft)**. Only a user with that permission can activate them, and activation is audited as `activate` with the approved price.                                                                                                                                                             | As requested. Staff can add products without publishing prices.                                                                                      |
| Concurrency in the UI     | Edits send the product `version`. On `VERSION_CONFLICT` a toast offers "Reload". Stock adjustments send the `stockVersion` shown.                                                                                                                                                                                                                                           | Two staff editing over the phone don't silently overwrite each other.                                                                                |
| Phones                    | Responsive layout. The sidebar becomes a drawer, and on small screens the products list is a card list (desktop keeps the table). On touch screens, inputs, selects and buttons get ≥44 px tap targets. Dark/light/system theme.                                                                                                                                            | Staff work on phones during the season.                                                                                                              |
| Performance               | Each screen is a lazily loaded chunk. Initial JS is about 99 KB gzipped (it was 268 KB before splitting). Lists use server-side paging, `keepPreviousData` and debounced search.                                                                                                                                                                                            | Fast on mobile data.                                                                                                                                 |
| Accessibility             | Labelled inputs with error text announced, a skip link, focus rings, `aria-pressed` toggles, `aria-live` price preview, keyboard-reachable reorder buttons (no drag-only actions), and confirmation dialogs for destructive actions.                                                                                                                                        | Spec requirement.                                                                                                                                    |

### Screens
